### Windows source regression and compatibility correction

Run [`39898671437`](https://github.com/caox233/FifthFreedom/actions/runs/39898671437)
at source `463aa521e5cdb3345e460442bacf8050bd42aef8` failed in the Windows

policy, so no traceback-based root-cause confirmation is claimed.

Source inspection found a concrete Windows incompatibility: CPython 3.12
[`win32_xstat` in `Modules/posixmodule.c`](https://github.com/python/cpython/blob/3.12/Modules/posixmodule.c)
maps path-stat `ctime` to creation time and applies extension-based executable
bits, while [`_Py_fstat_noraise` in `Python/fileutils.c`](https://github.com/python/cpython/blob/3.12/Python/fileutils.c)
retains the handle's change time and lacks extension-derived mode bits. Comparing
their complete tuples can reject an unchanged file. This explains a reproducible
compatibility defect; a subsequent real Windows run was required to confirm that
the observed source-check failure was resolved.

The assembler now binds Windows path/handle metadata using device, inode,
non-executable mode bits, link count, size, modification time and creation time.
Each API's full before/after metadata, including mode and `ctime`, still must
match. Linux retains the original complete cross-API comparison. No method is
removed or newly skipped; the production assembly command remains Linux-only.
All **21 focused builder methods passed locally**, including simulated Windows
metadata differences, changed identity/metadata rejection through both readers,
and retained Linux mode/ctime rejection. These are regression checks, not a
hosted Windows result or full-package admission.
