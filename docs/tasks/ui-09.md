# UI-09 — Windows retained overlay session prerequisite

Status: **ready-for-agent**. Ordinary Public remains closed. This is the next
Windows ownership prerequisite after [UI-08](ui-08.md), not completion of the
live overlay lease or the six project goals.

The [pinned source patch pair](../dependency-patches/easytier-2.6.4-windows-session/README.md)
adds a real backend session observer and connects it to EasyTier's actual Windows
TUN creation path behind a separate development feature. The observer obtains
identity from the retained Wintun Session/Adapter, checks kernel LUID/GUID/index/
alias and optional current IPv4 state, and becomes permanently invalid when its
owner or receive worker ends or an observed identity/liveness check fails. It
holds only a Weak Session reference and cannot create a UI-08 transport lease.

Six executable pure Rust tests cover strict request names, owner loss while other
session references survive, weak-reference lifetime, all identity component
changes, sanitized kernel/worker failure and a late successful read after owner
revocation. The patched Windows backend with its actual async module passed
`cargo check --locked --features async --target i686-pc-windows-msvc` locally.
Both patches applied and reversed to exact original SHA256 values. The full
EasyTier caller passed a syntax parse only; it has not been built for Windows.
No driver, core, game, network or TUN was started for this task.

The official API imposes a concrete boundary. In Wintun 0.14.1 source at tag
commit `bfef136abfa1665c2592be09a7e383d646cdbe6e`, `api/adapter.c`'s
`NciSetAdapterName` handles a duplicate name by renaming the conflicting adapter;
`WintunCreateAdapter` invokes `DriverInstall`; `WintunCloseAdapter` queues orphaned
device cleanup. The requested GUID is not treated as an authoritative returned
interface GUID. In Rust wintun 0.5.0, `get_guid()` caches the request while
`get_luid()` queries the actual retained handle. These were source reads, not a
reproduction of the bundled DLL or actual driver behavior.

The new mode therefore **requests a new adapter without `Adapter::open`**, but
does not promise collision-free exclusive creation or zero unrelated system
effects. Its feature suppresses the extra firewall/registry calls in
`virtual_nic.rs`; official-driver effects, remaining interface/DNS/route changes
and a trustworthy installation directory still require explicit development
environment review. A wrapper cannot erase these API effects. A new custom
Wintun DLL, signed-driver product or additional empty admission factory was not
introduced.

Next executable work is a separate full Windows candidate build with the exact
paired patches and patched dependency resolution, followed by synthetic/local
driver execution only in an explicitly authorized disposable Windows environment.
That run must verify actual returned identity, owner shutdown, down/rename/address
loss and precise side effects. Local owner IPC, secure-peer/process monitoring,
all game sockets and a reviewed production live-lease issuer remain unresolved;
the ordinary Public gate must not be opened from a name, snapshot, configuration
IP or return-pipe heartbeat.

The follow-up now has its own GitHub-hosted Windows 2025
[build-only workflow](../../.github/workflows/easytier-windows-build-only.yml).
The [separate recipe](../../scripts/easytier-windows-source.lock.json) pins the
existing Linux six-patch guard recipe, both UI-09 patches, the exact tun Git
archive and a narrowly scoped modern-Windows build patch. It leaves existing
Linux/runtime pins unchanged. Source preparation was actually run against both
canonical archives: 700 EasyTier files and 49 tun files, with combined source
SHA256 `0e01b494704e7a4f3afb67d7c54b446149fda7317938623d36164d0d53c0d1eb`.

The only restored held binary input is the already pinned x64 `Packet.lib`
import library retained only in the private build workspace for linking. Its
permission/provenance hold is not lifted, and it is never an uploaded artifact. The local Cargo path override is fixed, and the
lock transformation removes only the exact pinned tun Git source entry. Actual
`cargo +1.95.0 metadata --locked` for the Windows target confirmed that the caller
has the new feature and resolves its `tun` dependency to this patched local
tree with `async`. The resulting lock SHA256 is
`93933b3d72622fb04692d11defdf1ebc5ed979c5feedefceb74114bd2db6b6fc`;
metadata left all prepared source bytes unchanged. This was dependency
resolution, not a local Windows codegen or link result.

The source review also found that pinned `thunk-rs` invokes `curl -LOkf` for
unverified VC-LTL5/YY-Thunks compatibility archives. The added build patch skips
only that call under the explicit UI-09 feature; ordinary upstream builds are
unchanged. This development candidate targets modern Windows with the installed
MSVC CRT/SDK and does not promise Win7 compatibility or official-binary
reproduction. The pinned protoc prerequisite prevents the EasyTier build script's
fallback protobuf download. Other Cargo build-script/dependency closure has not
been declared complete.

Twelve focused source/receipt regressions pass locally, covering real patch
application, guard retention, exact paired resolution, lock changes, source
mutation, unexpected binary inputs, PE identity and sanitized failure receipts.
The hosted step will execute an actual locked release build of both core and CLI,
then statically inspect their AMD64 PE headers and hashes. It never runs those
executables, loads their DLLs, starts overlay networking or installs a driver. Only the
three explicitly named source/build receipts are uploaded. The full hosted
compile/codegen/link success has not yet been established.

and passed afterward. Fourteen focused tests now pass. Fixed producer stages
