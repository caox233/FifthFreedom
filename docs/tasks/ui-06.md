# UI-06 — owned native authentication return channel

Status: ready-for-agent — launcher implementation and portable checks present;
Windows synthetic-child validation and native-half integration pending.

The Public session reader needs the token produced by the native game login.
An account password/token cannot substitute for that token. This change adds an
optional channel to the existing launch service; Public UI and game activation
remain gated by owned overlay, runtime provenance, and actual source routing.

## Launcher boundary

`GameLaunchService.StartGameAsync` accepts an optional `PublicNativeReturn`.
Every launch removes inherited `FF_PUBLIC_RETURN_V1`; only an explicitly supplied
context may replace it. The descriptor contains a fresh random pipe name, launch
ID, launcher PID/creation time/path and verified package launcher hash. It contains
no password, token or challenge and is not itself a new trust root. The native
half must compare the descriptor against its independently verified package
launcher role and the pinned actual configuration-pipe server process, then
require the return pipe to have that same server identity.

The launcher duplicates the exact initial `Process.Start` handle, checks image
path and retains its kernel process identity. A separate event after the original
configuration ACK byte `1` grants admission only to that PID and creation time.
The preexisting diagnostic `PeerValidated` event is insufficient. The original
little-endian configuration frame and ACK wire are unchanged. `LaunchPipe` has
been mechanically extracted into its own production source file for direct tests.
Retail successor processes retain the existing LAN configuration delivery rules,
but do not acquire Public return permission by filename, directory or time window.

The return server uses an unpredictable name, `CurrentUserOnly`, kernel peer PID,
one connection, bounded frames and owned-handle liveness. It never searches for or
terminates other processes. EOF, process exit, invalidation and disposal cancel the
current UI05 context and its outstanding HTTPS requests. Reconnection retains the
latest auth generation and permits only an identical same-generation state replay.
A failed newer auth context cannot revive the previous login on reconnect.

## Exact protocol and identity provenance

Every frame is a 4-byte little-endian length followed by strict UTF-8 JSON, at
most 8192 bytes, schema `1`. Unknown/duplicate fields and invalid numeric shapes
are rejected. Frames have a five-second total read/write deadline. Native
heartbeats are expected every two seconds; five seconds without a complete frame
closes the launcher context (a stricter bound than the eight-second maximum lease).
Connection, ACK admission, challenge and hello also share a ten-second total deadline.

1. Launcher: `kind=challenge`, `launch_id` (32 lowercase hex), `challenge`
   (64 lowercase hex). Sent only after owned-process/config-ACK admission.
2. Native: `kind=hello`, same `launch_id` and `challenge`, plus the actual
   `game_instance` nonce (32 lowercase hex). This nonce stays pinned for that run.
3. Native: `kind=invalidate` or `kind=heartbeat`, positive `generation`.
   `authenticated` additionally carries `account_id`, `username`, `token` (<=4096).
   Every native auth state transition advances the generation; heartbeat does not.

`account_id` is the opaque actual `LoginResponse.user.id` (strict UTF-8 <=64 bytes,
nonempty, no controls), not the numeric database ID. Both it and the ASCII
username must match the independently captured launcher login account anchor.
Run/source/package/product/observer values also remain bound to the launch inputs.
The numeric `user_id` is explicitly unverified token metadata in the new
`FromOwnedNativeResponse` factory (`HasIndependentNumericUserId=false`). The UI05
strict constructor still requires its independent expected numeric ID. Neither
factory verifies signatures: the protected HTTPS server remains the signature,
source, expiry, revocation and database identity authority. Missing account or
native handoff remains closed; no password/account-token fallback exists.

`QueryCurrentAsync` uses the real UI05 protected HTTPS reader with the current
owned native context. No MainWindow activation or existing native configuration
wire change is part of this launcher work. The native publisher and independent
launcher identity checks are a coordinated implementation, not inferred from a
successful managed unit test.

## Verification

Run:

```
dotnet run --project tests/PublicNativeReturn/PublicNativeReturn.csproj -c Release --no-launch-profile
dotnet run --project tests/PublicSessionControl/PublicSessionControl.csproj -c Release --no-launch-profile
```

Local launcher receipts: 14 portable cases passed; 11 Windows-only cases were
explicitly skipped on Linux. The existing UI05 real-loopback-TLS suite passed all
15 cases, UI source contracts passed 12, and WPF cross-compilation completed with
zero warnings/errors. These are not hosted Windows IPC results.

The managed suite links the actual production protocol, process owner, return
server, context, package and TLS client. Linux runs portable framing, generation,
provenance and lifecycle tests (including actual pending loopback TLS query
cancellation through the return-state context); Windows-only cases are explicitly skipped there.
Windows additionally runs real kernel named-pipe/owned synthetic-child checks,
including PID/image/creation mismatch, pre-ACK rejection, startup/heartbeat
deadlines, EOF/reconnect/run exit,
and the actual original configuration pipe with good/bad/missing ACK. The config
pipe test substitutes only unrelated diagnostic projection and its executable-name
constant; it copies its own test apphost under a synthetic allowed name, never a
game binary. All children and directories are uniquely owned and cleaned up.

WPF cross-compilation does not prove Windows IPC execution. Hosted Windows results
must be recorded separately before claiming the child-process checks passed.
There is no game launch, driver installation, deployed endpoint, production token,
or claim that the encrypted overlay or Public runtime is ready.
