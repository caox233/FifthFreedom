# UI05 — Protected read-only native session client

Status: ready-for-agent — implementation and independent review complete; hosted Windows validation pending.

This implements the launcher's post-native-auth HTTPS session reader and its
strict input boundary. Public selection, readiness and game launch remain
disabled. The native game-token handoff to the launcher is still missing; this
batch does not change the existing named-pipe protocol or invent a login route.

## Actual integration boundary

The current production `AuthService.LoginAsync` performs retained native account
login and returns only the account ID. It does not return a native game-run token.
The game token is held by native hooks for authenticated metadata after native
authentication. The existing `LaunchPipe` in `Services/GameRuntime.cs` and
`hooks-config/src/launch_pipe.rs` transfers startup state; it is not an admitted
native game-token return channel.

The existing HTTPS control contract is only `POST /v1/sessions`. Its server checks
the native token signature, expiry, kernel-observed source, package, live run,
account revocation and observer grant before its read-only database query. It has
no login, registration, token issuance or password route. Account credentials and
account-purpose tokens cannot be upgraded by this client.

Two production files provide the concrete seam for a future reviewed native
handoff, without UI placeholders:

- `PublicSessionContext.cs` accepts an explicit deployment profile, the actual
  verified `ReleasePackage`, a typed Public `CredentialIdentity`, explicit native
  endpoint, caller-owned run expectations and the original native game token.
  The credential must match the deployment, endpoint and expected username.
  Expected user ID, source IPv4, product, run nonce and observer request are
  independent inputs; a future handoff must derive these from the owned native
  launch/overlay lease, not decode a token and compare it with itself.
- `PublicSessionControlClient.cs` binds requests to that deployment's configured
  HTTPS origin. `QueryAsync` accepts the session context and returns immutable
  read-only session/member collections. No caller-supplied alternative URL,
  issuer key, password, source header, account-token fallback, retry or automatic
  transport selection exists. Fast/Compatible and LAN Host/Join are separate
  concerns and do not change this protocol.

The local v1 envelope parser rejects noncanonical encodings, duplicate/unknown
claim fields, account/missing-game-run tokens and mismatched expected
user/source/product/run/package/observer values. It only screens purpose and
context. It does **not** verify signatures, decide expiry/admission, authenticate the
server, infer native process ownership or replace server-side authorization.
`PublicNativeGameSession` deliberately does not call itself verified proof.

A context binds the credential namespace, including deployment ID, HTTPS origin,
overlay network and native endpoint. Its source must be a usable address in that
configured overlay. Configuration identity is not publisher authentication.
The normal TLS endpoint and the native token's observed connection source must
still agree at the real server. This client does not install an overlay, select
an interface or prove an owned overlay is live. The later owned-runtime adapter
must establish and retain that route; a mismatched actual source is rejected by
the existing control server rather than accepted from a header.

## Concrete network and response behavior

The public constructor uses standard platform TLS certificate-chain and hostname
validation. Redirects, cookies, proxies and automatic decompression are disabled.
Even the internal test constructor rejects certificate-acceptance callbacks.
Requests use exact HTTP/1.1, `application/json` without charset, a known content
length, `Connection: close` and the caller's bearer only. The body contains exactly
`protocol_version=1`, all four package roles with verified release/compat/catalog
identity, and `observer_requested`.

The client accepts only HTTP 200, the exact JSON media type, no transfer/content
encoding, a known 1–524288 byte body and `Cache-Control: no-store`. Non-200 and
redirect responses fail without copying their bodies into exceptions. Connection
setup is bounded to three seconds and the entire request/body read to eight;
caller cancellation and context/client disposal also cancel requests. A final
cancellation check prevents a late response from publishing a disposed run's
snapshot.

The response parser requires exactly `schema=1` and `sessions`; each session and
member has the exact existing Python reader fields. It rejects duplicate keys,
invalid integer types/ranges, duplicate session IDs, conflicting member IDs/IPs,
foreign gameplay modes, missing host/requester membership, an incorrect local
source and addresses outside the configured overlay. At most 2048 sessions and
4096 total members are admitted. An empty current-session projection is valid.

Token/context representations are fixed text, errors use fixed codes without
inner network exceptions, and no token, password or account detail is logged or
persisted. Disposing a context cancels outstanding work and drops its token
reference; managed immutable strings cannot promise physical memory erasure.

## Remaining executable work

### Hosted Windows synthetic certificate correction

The original Windows candidate failed in case 05, the positive TLS query. Run
`39909129801`, job `120267789393`, retained the fixed diagnostic
`PublicSessionControl:05:TRANSPORT_FAILED:TLS:AuthenticationException:NO_CREDENTIALS`.
The synthetic fixture attached an `RSA.Create` private key directly with
`CopyWithPrivateKey`, leaving an ephemeral Windows key. Microsoft's
[SslStream troubleshooting guidance](https://learn.microsoft.com/en-us/dotnet/core/extensions/sslstream-troubleshooting#handshake-failed-with-ephemeral-keys)
explicitly identifies Windows Schannel `0x8009030E` for certificates with ephemeral
keys; the same guidance was read from the official
[dotnet/docs source](https://github.com/dotnet/docs/blob/main/docs/core/extensions/sslstream-troubleshooting.md).
The official [Windows certificate implementation](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/X509Certificates/CertificatePal.Windows.PrivateKey.cs)
also shows `CopyWithPrivateKey(RSA)` falling back to `CopyWithEphemeralKey` when
the RSA instance has no persisted key container.

Only the Windows synthetic server leaf is now exported to an in-memory PFX and
reloaded with `X509CertificateLoader.LoadPkcs12` using `UserKeySet`, without
`PersistKeySet` or `EphemeralKeySet`. This gives Schannel a user key container that
certificate disposal deletes. The temporary PFX bytes are zeroed in `finally`;
no PFX is written or uploaded. The official
[Windows loader source](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/X509Certificates/X509CertificateLoader.Windows.cs)
defines this disposal behavior in `ShouldDeleteKeyContainer`.

The certificate identity, custom-root test policy, standard hostname check and
production client are unchanged. Linux regression results do not prove this
Schannel correction: the next actual Windows run must pass the positive query
and the untrusted-CA/wrong-hostname negative cases. Later UI06/UI07 work supplies
the separate owned return/preparation seams; it does not open Public readiness.
After this fixture-only correction, the local TLS suite still passed all 15 cases
and the return suite passed 14 portable cases with its 11 Windows-only cases
explicitly skipped. These receipts are regression evidence, not Windows proof.

Define and implement a versioned token handoff from the current owned game
process: explicit process/launch identity, existing pipe ACL/PID guarantees,
cancellation and bounded lifetime, no diagnostic snapshot/export of tokens, and
no account-purpose fallback. Preserve the accepted startup pipe/package/capability
contracts while testing the added return channel separately. Only after that
handoff, owned encrypted-overlay liveness and runtime/provenance gates are proven
can the Public adapter call this reader from production UI flows. This batch
starts no game, capture, driver, external deployment or Release.
