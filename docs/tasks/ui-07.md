# UI-07 — final-login observation and prepared configuration ownership

Status: ready-for-agent — implemented and independently reviewed; the original nine
final-login checks passed on hosted Windows at568c3c5. Public runtime composition
remains incomplete.

The initial UI account login is not the final connection used to prepare game
configuration. `HookConfigService` performs a second actual login after verifying
the deployed package. Previously its response was discarded when it returned a
bare configuration pipe. A future Public return channel needs that final account
identity without reconstructing it from request fields or the native token.

`PrepareConfigurationAsync` now returns one `PreparedGameConfiguration` owner:

- The exact original `LaunchPipe`, with unchanged configuration bytes and ACK wire.
- `FinalLoginObservation` containing actual final response `User.Id` and
  `User.Username`, the immutable verified `ReleasePackage`, and a historical API
  socket observation when available. No password or account/native bearer is
  retained in observation metadata, representations or logs.

`LanConnection` captures local/remote addresses and ports directly from a
successfully connected API HTTP/2 socket. This records a connection fact, not a
live interface lease or proof of encryption/source routing for another native
process. The connection is disposed when final configuration preparation ends;
the observation deliberately remains historical. There is no config-IP fallback.

The actual `GameLaunchPreparation` path consumes the prepared owner and transfers
its pipe only after the existing launch service confirms adoption. A failure in
`beforeStart`, a rejected launch, or disposal before transfer clears that pending
pipe only. Successful transfer makes later prepared-owner disposal inert. The
existing `HookConfigService.PrepareAsync` remains a compatibility wrapper returning
the identical pipe with ownership transferred to its caller.

LAN checks are retained: package/deployed-main verification, native password
contract, capabilities/config port 80, gameplay mode, final opaque account-ID
comparison and `AssertRouteUnchanged`. The frame continues to use the original
caller values. An empty returned username remains an observed empty value and
does not introduce a new LAN acceptance rule; a future Public account anchor
would reject missing identity. No Public context is attached to the current UI.

## Verification and remaining gate

```
dotnet run --project tests/FinalLaunchPreparation/FinalLaunchPreparation.csproj -c Release --no-launch-profile
```

Nine local tests passed using a fresh owned loopback HTTP/2 gRPC server and actual
production authentication, transport, config preparation and pipe ownership.
They distinguish initial and final responses, compare the captured socket
endpoints to the actual server-side final request, check compatibility-wrapper
frame bytes, preserve mismatch rejection, and exercise failure/success ownership
across `beforeStart`. No game process or runtime deployment is performed; only
the forbidden process-start/deployment boundary and unrelated diagnostics are
substituted. The server binds only loopback, including port 80 required by the
retained contract; inability to bind is a failure, not a successful skip.

WPF cross-compilation passed with zero warnings/errors. Hosted Windows results
remain separate from this local portable evidence.

A callable Public launch bundle still needs a concrete, currently owned Windows
overlay capability tied to its exact process and interface generation, explicit
deployment/credential context, and actual native source-route enforcement. No
such provider is fabricated here. Runtime hashes, this historical socket record,
or the address from configuration cannot substitute for that capability. The
unavailable Public adapter remains closed. Future attachment must bind the live
capability and deployment to this same prepared attempt and revalidate after the
`beforeStart` await, before transferring the UI06 return channel to the session.

## Actual Windows follow-up

The [568c3c5 prerequisite run](https://github.com/caox233/FifthFreedom/actions/runs/39915438709)
passed the unchanged nine real final-login checks on Windows. The owned runner's
default IIS site had occupied port80. Scoped preparation verified that site's
identity and exact HTTP80 member, stopped it, proved an owned bind, then restored
the recorded Started state after the test. Extra default WCF bindings did not
change its identity. No production port, port exclusion or other site was changed.

The prior actual port failure is retained; the successful check does not stand in
for full component compilation, native pipe interoperability, a live overlay
capability or gameplay. The bounded [official receipt](../evidence/hosted-windows-loopback-568c3c5.json)
records both preparation and restoration. The callable Public provider described
above remains unavailable until the missing live ownership boundaries are built.
